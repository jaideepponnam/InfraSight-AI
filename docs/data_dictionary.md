# InfraSight-AI data dictionary (telemetry plus SRE Milestone 1)

The original seven telemetry tables below retain their schema and semantics.
Migration 0003 adds six independent SRE tables, described at the end of this document.

For SRE API contracts, lifecycle semantics, and local review, see
[sre_milestone1.md](sre_milestone1.md).

## Identity and source convention

source_id is a stable ingestion-source identifier, not a provider name or per-run identifier. Examples: simulated-cloud, host-local, ibm-cloud-account-a-collector, aws-account-a-collector, azure-subscription-a-collector, and gcp-project-a-collector. Keep it unchanged across restarts and replay. A future provider can have many source IDs representing accounts/collectors. There is intentionally no sources table in Phase 2.

regions.provider identifies the provider family (simulated, host, or future cloud provider). Server identity is the pair (source_id, external_server_id). Provider identity is available through servers.region_id; it is not independently duplicated on servers.

## Shared conventions

- UUID primary keys identify regions, servers, and ETL runs. PostgreSQL gen_random_uuid() supplies defaults.
- Raw events, metrics, and rejections use BIGINT GENERATED BY DEFAULT AS IDENTITY keys for compact high-volume references.
- All timestamps are TIMESTAMPTZ. Clients must provide timezone-aware timestamps; application processing will normalize to UTC. PostgreSQL retains the instant, not the original timezone name.
- All foreign keys use ON DELETE RESTRICT. ORM relationships have no delete cascade. Retention requires explicit deletion in dependency order; removing inventory must never silently erase history.
- Timestamp defaults use CURRENT_TIMESTAMP. updated_at has an initial default only; write operations explicitly update it.
- JSONB fields use none_as_null=True: missing optional values are SQL NULL, not JSON null.
- Identity strings must be nonblank. Source adapters must use canonical, consistent identifiers.
- Monetary values use NUMERIC(18,8), avoiding binary floating-point rounding and preserving small micro-batch interval costs.

## Observation and cost semantics

observed_at is the interval start; interval_seconds is its positive duration. estimated_cost is the estimated cost for that interval, not an hourly rate. Sum only non-overlapping intervals within the reporting window. Future ETL must align/split intervals at reporting-day boundaries and ensure consistent interval lengths; the current schema prevents duplicate starts but does not implement a range exclusion constraint.

CPU, memory, and storage are percentages in [0,100]. Network is Mbps. Uptime is seconds. Unknown network, uptime, or cost values may be NULL, enabling a truthful optional host adapter. Cost and currency must be both present or both absent. Currency is a three-uppercase-letter code; this is format validation, not an exhaustive currency registry. Negative and nonfinite measurements are rejected by checks or numeric type limits. NaN is explicitly excluded by finite comparisons.

Statuses: RUNNING, DEGRADED, STOPPED, FAILED. Health: HEALTHY, WARNING, CRITICAL. Phase 2 restricts allowed values; future transformations decide how status and utilization derive health. Environments: dev, staging, prod.

## Idempotency and event ownership

- regions: unique (provider, region_code).
- servers: unique (source_id, external_server_id).
- raw_telemetry: unique (source_id, source_event_id).
- infrastructure_metrics: unique (server_id, observed_at) and unique raw_telemetry_id.
- data_quality_rejections: unique (etl_run_id, raw_telemetry_id).

The extraction envelope must provide source_event_id even for invalid payloads. Adapters without native IDs must derive a stable key. The first raw payload is preserved; event corrections need a future explicit reconciliation policy. A replay does not reassign the original raw event to the later run. Metrics refer to the run that first inserted the cleaned observation. Rejections are attempt-specific, so a later run can record another rejection of the same raw event.

## ETL accounting and lifecycle

QUEUED → RUNNING → SUCCEEDED or FAILED is the intended lifecycle. Checks validate status membership, terminal timestamps, timestamp order, nonnegative counts, count bounds, and successful reconciliation; the Phase 3 pipeline implements the intended transitions; checks do not implement a generalized transition engine.

records_extracted counts records presented to validation; records_accepted counts valid records including duplicates; records_inserted counts newly created metrics; records_duplicated counts valid records that create no new metric; records_rejected counts invalid records. A successful run requires extracted = accepted + rejected and accepted = inserted + duplicated. Failed/in-progress runs may have incomplete accounting. Writers update related counters together.

error_code/message/details must be sanitized before persistence. Never store credentials, access tokens, or full connection URLs in error fields.

## Incremental progress

ingestion_state stores a watermark, an opaque JSON cursor, or both, according to adapter semantics. New sources can have neither. etl_runs records before/after values plus the requested half-open extraction window [start,end).

Phase 3 ETL holds a dedicated session-level source lock, uses an overlap window, commits batches, and advances progress only after success. A failed run may have committed batches; replay is safe through unique constraints. Progress must not move backward. The database foreign key validates run existence; the ETL transaction must also ensure last_successful_run_id actually references a successful run of the same source. Likewise, the Phase 3 pipeline constructs consistent inventory/raw/run references from source context; this is not a cross-row CHECK.

## Index strategy

Metrics have server/time descending indexes for latest state and server history, plus time/server for bounded fleet analytics. Inventory uses region/environment and environment indexes. Run status/request-time indexes support future worker selection and source run history. Raw/rejection run/event indexes support audit joins; extraction/rejection timestamp indexes support retention. Unique constraints provide their own indexes. Cost/health filtering initially uses bounded time scans; add specialized indexes only after representative query plans justify them.

## Verification safety

Schema and migration tests create a uniquely named infrasight_test_<UUID> database on the container via TEST_DATABASE_URL. They migrate that disposable database, isolate record changes in transactions, and delete only the created database afterward. The test account needs CREATEDB permission. Upgrade of the application database is explicit. Downgrade verification never targets application data or the existing Windows PostgreSQL services.

## Phase 3 implementation notes

The schema is unchanged at revision 0001. Phase 3 implements source-scoped session advisory locks, batched conflict-aware loading, raw-first validation, rejection attempt evidence, committed run counters, and atomic success/progress finalization. Before/after cursors describe committed progress; timestamp adapters restart their page cursor for each extraction window. Older replays preserve the forward watermark/cursor but become the latest successful audit attempt.

Phase 3 validates provider consistency within an adapter and constructs source/run/server/raw relationships from trusted pipeline context. Historical inventory metadata is protected against older replay. Raw payloads are preserved verbatim as JSON-compatible source records; malformed observed_at does not affect simulator extraction membership. Missing required host percentages produce rejections. Full transaction and health semantics are in docs/etl_design.md; the recorded demo is in docs/phase3_demo.md.

## Phase 4 analytics extension

Database head 0002 adds an analytics schema without changing the seven domain tables introduced by 0001. Six public normal views expose approved business datasets; a private helper performs UTC interval allocation. No public view depends on custom session settings. Parameterized AnalyticsService queries implement runtime reference times, freshness thresholds, currencies, windows, pressure/optimization rules, and comparisons. Raw payloads, rejection details, and internal errors remain outside the public analytics contract.

The exact business definitions, coverage/cost assumptions, per-view columns, and limitations are in docs/analytics_dictionary.md. Recorded database answers and inspection queries are in docs/phase4_demo.md. Existing indexes were measured; no new index was added.

## SRE incident domain (migration 0003)

The following six tables are independent of the telemetry graph. Every ID and foreign
key is UUID, generated IDs default to gen_random_uuid(), and foreign keys use RESTRICT.
All timestamps are TIMESTAMPTZ. Evidence is required JSONB written by the backend;
raw HTTP bodies, API keys and plaintext capabilities are excluded.

| Table | Principal columns and semantics |
| --- | --- |
| sre_services | id, unique service_key fixed to controlled-application-dependency, description, created_at |
| sre_demo_runs | id, service_id, scenario=http-503, idempotency_key, status, phase, probe_token_hash, fault_enabled, fault_expires_at, fault_cleared_at, deadline_at, finished_at, error_code, created_at |
| sre_probe_results | id, run_id, phase, observed_at, duration_ms NUMERIC(12,3), nullable http_status and target_request_id, outcome, initiating request_id, evidence |
| sre_incidents | id, service_id, run_id, fingerprint, title, severity=SEV3, state, policy_version, detected_at, acknowledged_at, resolved_at, version |
| sre_incident_events | id, incident_id, sequence, event_type, actor, from_state, to_state, request_id, evidence, created_at |
| sre_recovery_attempts | id, incident_id, idempotency_key, action=clear-controlled-dependency-fault, status, error_code, action_applied, evidence, request_id, started_at, finished_at |

Run status is ACTIVE/SUCCEEDED/FAILED/INTERRUPTED; phase is
CREATED/BASELINE/FAULT/DETECTED/RECOVERY/COMPLETE. An ACTIVE row can be past its deadline
until the next admin operation reconciles it. Effective fault behavior always checks
the deadline, regardless of the stored fault_enabled flag.

Probe phases are BASELINE/DETECTION/VERIFICATION. Outcomes are HEALTHY, HTTP_503,
UNEXPECTED_HTTP, TIMEOUT, TRANSPORT_ERROR or INVALID_RESPONSE. Only an actual 503 response
with the correct controlled-workload body can become HTTP_503. Duration is measured
with a monotonic clock. observed_at marks the probe's wall-clock start. Target request
IDs identify actual HTTP responses; transport failures can have no target request ID.

Incident states are DETECTED/ACKNOWLEDGED/INVESTIGATING/MITIGATING/VERIFYING/RESOLVED.
Each event increments the incident version and records its sequence transactionally.
Actors identify admin-key, admin-exercise-runner or system roles, not individual people.
Detection events reference triggering probe IDs and a versioned policy. Recovery events
reference the attempt and fresh diagnostic/verification probes.

Recovery status is RUNNING/SUCCEEDED/FAILED/INTERRUPTED. action_applied distinguishes
executing the sandbox action from reverifying a prior action. SUCCEEDED requires
healthy post-action probes; clearing a flag alone is insufficient.

Unique indexes permit one ACTIVE run per service, one unresolved incident per
fingerprint, and one RUNNING recovery per incident. Request idempotency is unique
within a service (run) or incident (recovery); event sequence is unique per incident.
